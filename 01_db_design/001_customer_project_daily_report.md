# 001 顧客・案件・日報・請求・支払のDB設計

## 目的

業務アプリにおける基本的なテーブル分割、ID設計、1対多の関係を理解する。

## 今回のテーマ

以下の5つを、どのようにテーブル分けして紐づけるか考える。

- 顧客
- 案件
- 日報
- 請求
- 支払

## 確認問題

### Q1

「顧客」と「案件」は同じテーブルに入れるべきか、分けるべきか。理由も書く。

### Q2

「1社の顧客が複数案件を持つ」とき、どんなデータ構造にするか。

### Q3

「案件ごとに複数の日報がある」とき、日報テーブルには何を保存すべきか。

### Q4

「請求書」と「案件」はどう紐づけるべきか。

### Q5

顧客名を直接いろいろなテーブルに保存すると、何が問題になりそうか。

## 回答欄

### A1

別。持つ役割が違う。

### A2

顧客に対してマスタIDを持たせて、それに案件を紐づかせる。

### A3

どの案件かのID。

### A4

案件のステータスが終了、または準ずるものに変更したのち、その段階での金額計算を行い出力する。

### A5

情報がばらばらで収集できない。登録の重複などが起きる。

## ChatGPT評価欄

### 理解度評価

初回評価：58%

- Q1：70%。顧客と案件を分ける判断は正しい。理由として「1顧客に複数案件がある」まで言えると強い。
- Q2：80%。方向性は良い。正確には、案件テーブル側に `customer_id` を持たせる。
- Q3：45%。`project_id` は正しいが、日報には日付・作業者・作業内容・作業時間なども必要。
- Q4：30%。回答がDB構造ではなく業務フローになっている。
- Q5：65%。重複・表記ゆれ・更新漏れ・集計ミスの観点が必要。

### 補正ポイント

DB設計では「データ構造」と「業務フロー」を分けて考える。

- データ構造：どのテーブルに何を保存するか
- 業務フロー：いつ作成・更新・出力するか

基本構造：

```text
customers
- id
- customer_name
- address
- phone

projects
- id
- customer_id
- project_name
- status
- contract_amount

daily_reports
- id
- project_id
- work_date
- worker_name
- work_detail
- work_hours

invoices
- id
- project_id
- invoice_date
- amount
- status

payments
- id
- invoice_id
- payment_date
- paid_amount
```

## 追加確認問題と回答

### Q6

「案件」と「請求書」が1対1ではなく、1案件に複数請求書が発生するケースはどんな場合か。

### A6

- 1案件の請求を複数回に分ける場合
- 出来高請求を行う場合

### 評価

理解度：85%。正解。出来高請求は分割請求の一種だが、業務上は別パターンとして考えてよい。

---

### Q7

「請求書」と「支払」は、1対1でよいか。それとも1対多になる可能性があるか。

### A7

多になる場合あり。分割支払いなどの可能性もある。

### 評価

理解度：80%。正解。1つの請求書に対して複数回の入金・支払が発生する場合があるため、支払テーブルは請求書から分ける。

---

### Q8

「支払」は、案件IDに紐づけるべきか。それとも請求書IDに紐づけるべきか。

### A8

案件ID。案件は請求も持つため、請求－支払いで残金額を出せるから。

### 評価

理解度：55%。考え方は惜しいが、基本は `invoice_id` に紐づける。1案件に複数請求書がある場合、支払を案件IDだけに紐づけると、どの請求書に対する支払か分からなくなる。

基本構造：

```text
案件 → 請求書 → 支払
```

---

### Q9

`payments` に `project_id` も一緒に持たせる設計はアリか。

### A9

親に紐づけるならなし。ただ、ないとどの支払いがどうなったかわからなくなりそうだからあり。

### 評価

理解度：75%。正解は条件付きでアリ。`invoice_id` が正本で、`project_id` は検索・集計・表示を簡単にするための冗長カラムとして持たせることがある。ただし手入力は禁止。`invoice_id` から自動セットする必要がある。

---

### Q10

`payments` に `project_id` を持たせる場合、手入力にすると何が危険か。

### A10

入力間違いが起きた場合、別の案件の支払いが済になってしまい、危険なことになる。

### 評価

理解度：90%。正解。冗長カラムは便利だが、手入力にするとデータ不整合が起きる。`invoice_id` から自動セットする、またはDB側/API側で整合性チェックする必要がある。

## 現時点まとめ

今回の到達点：

```text
顧客 → 案件 → 請求書 → 支払
       └→ 日報
```

理解できたこと：

- 顧客と案件は分ける
- 1顧客に複数案件がある
- 1案件に複数日報がある
- 1案件に複数請求書がある場合がある
- 1請求書に複数支払がある場合がある
- 支払の基本親は請求書
- `project_id` のような冗長カラムは条件付きでアリ
- 冗長カラムを手入力させると不整合が起きる
